# ЛР 1. Dockerfile

Приложение: небольшой веб-сервис на Flask со счётчиком посещений. Адрес `/` увеличивает счётчик и возвращает `Visits: N`, адрес `/health` отвечает `ok`. Счётчик хранится в файле `/data/counter.txt`. Папка `/data` подключается как volume, поэтому значение переживает удаление контейнера.

| Файл | Что это |
|------|---------|
| `app/app.py` | код приложения |
| `app/requirements.txt` | список библиотек с версиями |
| `Dockerfile.bad` | плохой Dockerfile, 8 ошибок |
| `Dockerfile.good` | хороший Dockerfile |
| `.dockerignore` | что не отправлять в сборку |

Каждый файл подробно прокомментирован внутри и читается самостоятельно. В `Dockerfile.bad` каждая ошибка объяснена рядом со строкой, где она допущена. Этот README: краткая сводка.

## Сборка и запуск

```bash
# плохой
docker build -f Dockerfile.bad -t lab1-bad .
docker run -d -p 5002:5000 --name bad lab1-bad
curl localhost:5002/          # Visits: 1

# хороший, с монтированием volume
docker build -f Dockerfile.good -t lab1-good .
docker run -d -p 5001:5000 -v lab1-data:/data --name good lab1-good
curl localhost:5001/          # Visits: 1
curl localhost:5001/          # Visits: 2
```

### Демонстрация volume

```bash
docker rm -f good
docker run -d -p 5001:5000 -v lab1-data:/data --name good lab1-good
curl localhost:5001/          # Visits: 3, данные сохранились в томе

docker rm -f bad
docker run -d -p 5002:5000 --name bad lab1-bad
curl localhost:5002/          # Visits: 1, тома нет, данные потеряны
```

## Плохие практики в `Dockerfile.bad` и их исправление

| № | Что сделано плохо | Почему это плохо | Как исправлено в `Dockerfile.good` |
|---|-------------------|------------------|------------------------------------|
| 1 | `FROM python:latest` | Тег `latest` со временем указывает на другую версию, сборка невоспроизводима. Полный образ весит больше гигабайта и содержит лишние программы, то есть лишние уязвимости. | `FROM python:3.12-slim`: версия зафиксирована, образ минимальный. |
| 2 | `ENV SECRET_KEY=supersecret123` | Всё из Dockerfile остаётся в образе. Секрет читается через `docker history` и лежит в git. | Секретов в Dockerfile нет. Они передаются при запуске: `-e`, `--env-file`. |
| 3 | `RUN apt-get update` и `RUN apt-get install -y vim nano curl git` отдельными командами | Слой `update` кэшируется и устаревает, установка новых пакетов потом падает. Ставятся ненужные программы. Нет `--no-install-recommends`, не удалён `/var/lib/apt/lists`. | Системные пакеты не ставятся, приложению они не нужны. В комментарии приведена правильная форма: одна команда `RUN` с очисткой. |
| 4 | `COPY app/ /app` до установки библиотек | Любая правка кода сбрасывает кэш слоя, и библиотеки ставятся заново при каждой сборке. | Сначала `COPY requirements.txt` и `pip install`, потом `COPY app.py`. |
| 5 | `RUN pip install flask` | Версия не указана, сборки в разное время дают разный результат. Кэш pip остаётся в слое. | `requirements.txt` с точными версиями, `pip install --no-cache-dir -r requirements.txt`. |
| 6 | Нет `USER`, процесс работает от root | Взлом приложения сразу даёт права администратора в контейнере и упрощает выход на хост. | Создан пользователь `appuser` (uid 1001), `USER appuser`. |
| 7 | Нет `VOLUME` и `HEALTHCHECK` | Данные теряются при удалении контейнера. Docker не знает, отвечает ли приложение. | `VOLUME /data`, `HEALTHCHECK` с запросом к `/health`. |
| 8 | `ENTRYPOINT python app.py`: shell-форма и отладочный сервер Flask | Главным процессом становится `/bin/sh`, сигнал остановки до приложения не доходит, контейнер убивается через 10 секунд. Встроенный сервер Flask не предназначен для эксплуатации. | Exec-форма и gunicorn: `CMD ["gunicorn", "--bind", "0.0.0.0:5000", ...]`. Остановка за 0.3 с с кодом 0. |

## Две плохие практики использования этого контейнера

1. **Запуск без volume.** Если запустить `docker run -d -p 5001:5000 lab1-good` без `-v lab1-data:/data`, счётчик пишется во временное хранилище контейнера. После `docker rm` и нового запуска он начинается с 1. Любые данные, которые должны жить дольше контейнера, нужно выносить в том или bind mount.
2. **Запуск с лишними правами.** Например, `docker run --privileged ...`, `--user root` или проброс `-v /var/run/docker.sock:/var/run/docker.sock`, «чтобы точно работало». Флаг `--privileged` даёт контейнеру доступ к устройствам хоста, а сокет Docker позволяет управлять всеми контейнерами. Это сводит на нет изоляцию и непривилегированного пользователя из Dockerfile. Сервису со счётчиком такие права не нужны. Правильно наоборот ограничивать: `--cap-drop ALL`, `--read-only` с отдельным томом для `/data`.

## Два случая, когда контейнеры использовать не стоит

1. **Приложению нужно своё ядро ОС или прямой доступ к оборудованию.** Контейнер использует ядро хоста. Если программе нужны собственные модули ядра, драйверы, другая операционная система (например, Windows-приложение на Linux-сервере) или сильная изоляция для запуска недоверенного кода, подходит виртуальная машина или отдельный сервер.
2. **Простое или сильно зависящее от диска приложение, где контейнер добавляет сложность без пользы.** Например, одиночная production-база данных на выделенном сервере, которой важна максимальная скорость диска и которую администрируют вручную: ошибка в настройке тома приводит к потере данных, а преимущества контейнеров (быстрое пересоздание, масштабирование) не используются. Или разовый скрипт на одной машине: писать для него Dockerfile дольше, чем запустить напрямую.
